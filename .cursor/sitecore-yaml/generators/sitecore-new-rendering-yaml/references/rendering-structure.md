# Headless rendering serialization structure

Template source: **NewComponent** branch under an existing collection (standard headless collection pattern).

**The generator only creates files under an existing collection module — nothing is created in Sitecore CM until `dotnet sitecore serialization push`.**

## Prerequisite

Collection YAML must exist (`authoring/items/{Collection}/` + `{system-name}.module.json`). Use **sitecore-new-collection-yaml** first if missing.

## Output layout

```
authoring/items/{Collection}/serialized-content/
├── renderings/{collection-system}/{ComponentName}.yml
├── templates/{collection-system}/{ComponentName} Templates.yml          # branch root
├── templates/{collection-system}/{ComponentName} Templates/
│   ├── {ComponentName}.yml                                              # datasource template
│   ├── {ComponentName}/
│   │   ├── Data.yml                                                     # section (default)
│   │   ├── Data/                                                        # fields (optional, not auto-generated)
│   │   └── __Standard Values.yml
│   ├── {ComponentName} Folder.yml
│   ├── {ComponentName} Folder/
│   │   └── __Standard Values.yml                                        # __Masters → datasource + folder
│   ├── {ComponentName} Parameters.yml
│   └── {ComponentName} Parameters/
│       └── __Standard Values.yml
└── project-settings/{collection-system}/{collection-system}/
    └── Add {ComponentName}s Data Item.yml                               # insert options rule
```

## Naming

| Input | Example | Used in |
|-------|---------|---------|
| Component name (PascalCase) | `CookieBanner` | `componentName`, template/rendering item names, TSX registration |
| Template branch folder | `CookieBanner Templates` | Sitecore template branch |
| Collection system name | `company-name` | Paths under `/Project/{system}/` |
| Insert-options rule | `Add CookieBanners Data Item` | `{ComponentName}s` plural |

**Component name** must match the Next.js component map `componentName` and the rendering `componentName` field exactly.

## Cross-reference wiring (automatic)

| Source | Target |
|--------|--------|
| Branch root `Parent` | `templates/{collection-system}.yml` ID |
| Rendering `Parent` | `renderings/{collection-system}.yml` ID |
| Insert-options rule `Parent` | `project-settings/{system}/{system}.yml` ID |
| Datasource `__Standard values` | Datasource std-values item ID |
| Folder std-values `__Masters` | Datasource + folder template IDs |
| Rendering `Parameters Template` | Parameters template ID |
| Rendering `Datasource Template` | Logical path to datasource template |
| Insert-options `Template` | Folder template ID |
| Insert-options `Location` | Headless bucket rule (fixed GUID — see [system-ids.md](system-ids.md)) |

## Template sections and fields

- **Sections** organize fields in Content Editor / Pages ([data template sections](https://doc.sitecore.com/sai/en/developers/sitecoreai/content-modeling-and-presentation/data-templates/data-template-sections.html)).
- Default branch includes a single **`Data`** section (`Data.yml` + empty `Data/` folder).
- Add fields under `Data/{FieldName}.yml` manually or via `--fields fields.json`.
- Use **multiple sections** when fields group logically (e.g. `Content`, `Settings`) — see [field-types.md](field-types.md).

Fields are **not** generated by default (only structure). Map TSX props → Sitecore field names when adding fields.

## GUID remapping

Every new item `ID:` in the generated YAML gets a **fresh random UUID**. Internal references (`Parent`, `Template`, `__Standard values`, `__Masters`, braced GUIDs in rendering fields) are updated together.

**Not remapped** (Sitecore foundation IDs):

- Standard template `{1930BBEB-7805-471A-A3BE-4858AC7CF696}`
- Rendering-parameters base templates (see [system-ids.md](system-ids.md))
- System template IDs for branch, datasource, data section, field definition, JSON rendering
- Insert-options bucket location `{BA2F959D-A614-4C92-8B57-F1FC1A323ABE}`

## Path hashing

When paths exceed `defaultMaxRelativeItemPathLength` (see `sitecore.json` and the [SCS configuration reference](https://doc.sitecore.com/sai/en/developers/sitecoreai/sitecore-content-serialization/configuration/sitecore-content-serialization-configuration-reference.html)), the CLI may store some files under hash folders on disk while siblings with shorter paths remain in readable folders. YAML `Path:` always stays the full logical Sitecore path. Deep field paths under `{ComponentName} Templates/.../Data/{FieldName}` often trigger hashing — run `validate --fix` after adding fields; never guess hash names or edit `Path:` to match disk layout.

**Do not re-create a field under the readable tree if it already exists in a hash folder** (or vice versa). That yields `NON-UNIQUE ITEM PATH` with two IDs for one Path; `validate --fix` cannot fix it. See [non-unique-item-paths.md](../../../references/non-unique-item-paths.md).

Item YAML format: [YAML serialization format](https://doc.sitecore.com/xp/en/developers/104/sitecore-experience-manager/the-yaml-serialization-format.html).

## Push / validate

Uses the **collection namespace**: `{collection-system}-scs`

```powershell
cd authoring/items/{Collection}
dotnet sitecore serialization validate --fix -i {collection-system}-scs
dotnet sitecore serialization push -n production -i {collection-system}-scs
```

## After push (manual / other workflows)

Prefer completing these **before** push so CM is usable on first sync. Full checklist: [site-authoring-wiring.md](../../../references/site-authoring-wiring.md).

1. Register TSX in editing host `component-map.ts` with same `componentName`
2. Placeholder settings + rendering `Placeholders` field for every TSX placeholder
3. Default datasource under site `Data/{ComponentName}s/` (field IDs from template YAML)
4. Add rendering to **Available Renderings**
5. Wire page layout / partial design `__Renderings` as needed
